# 使用流程与远端依赖整改方案

> 2026-10-16。P0-A/B/C 与 P1 的运行时代码和本地自动化验证已完成，包含 connect、session_id、ready、takeover/resume 与 Bash >=3.2 配置。真实堡垒机与两名首次使用者验收尚待完成；逐项证据见 [整改验证记录](remediation-validation.md)。安装旧包时仍须先检查 capabilities，不能根据本文推断已安装版本的能力。可选 P2 sh-v1 尚未实施。

## 结论

操作复杂首先需要改产品设计：现有实现把内部协议的操作步骤交给了用户。建议保留 TypeScript + Bun、tmux 和执行事务核心，优先重做入口、交接和恢复流程。Bash 兼容范围单独验证，不作为操作简化的发布前提；可移植 sh 协议留待实际目标环境需求确认后实施。

优先交付“一个命令连接、人工登录、一次明确交给 Agent 的确认”。用户通过 session_id 指定共享会话；单会话时由 Agent 自动读取，不要求用户提供 hostname。用户不需要学习 shell-init、控制权状态、锁范围或命令请求编号。认证、目标选择和异常时的决策仍由用户负责，工具负责完成这些决策背后的机械步骤。

### 本轮评估的主要调整

原方案的入口封装方向合理，但不能只增加四个命令别名。需要补齐以下产品行为，才能真正减少操作：

| 当前摩擦 | 核对到的实现或文档 | 整改决策 |
|---|---|---|
| 安装说明先要求构建、测试 | README 的安装入口面向开发者 | 普通用户先看到已验证平台的独立二进制安装说明，源码开发另列；发布前保留真实的构建方式 |
| 普通用户仍看到 JSON 和 19 个平铺命令 | `src/cli.ts` 的 help 与 emit | 默认展示短文本、当前状态和一个下一步；完整命令放到高级帮助，保留机器 JSON |
| 容易以为必须手写配置 | README 要求复制配置；`src/config.ts` 已有无配置默认值 | 单会话首次使用不要求配置文件，也不要求学习 socket/pane |
| 创建、登录、初始化、校验、交接割裂 | README 的首次执行流程 | connect 负责进入终端，ready 负责完整准备事务 |
| 连接别名与目标服务器容易混淆 | `Sessions.start` 遇到已有别名直接返回绑定 | 区分 SSH 入口、Bridge 会话与最终目标；新入口禁止静默复用不明目标 |
| 已登录后仍要提供 hostname | confirm-shell 要求 expected-host | 新入口使用 session_id 选择本次交接会话；hostname 自动读取用于展示，高级预期主机检查可选 |
| Agent 不知道如何调用 Bridge | 只有集成文档和 AGENTS.md 示例 | 随包提供可安装的通用 skill；加载后执行能力检测、会话选择、交接与恢复 |
| 再次交接和异常处理要重学底层流程 | handoff 撤销确认；recover 与 recover-lock 分离 | 用户只表达接管或恢复意图，工具定位请求、检查锁、重新准备 |

下文保留整改前的静态评估和 Bash 3.2 局部实验作为设计背景；当前代码和自动化证据见验证记录。操作次数和两分钟时间仍是首次使用者验收目标，不把开发环境的自动测试当作可用性实测成绩。

## 现状与原因

### 操作复杂是接口问题

目前 README 的首次执行路径是：

```text
start → attach --writable → 手动 SSH/MFA/菜单
→ 第二个本地终端运行 shell-init → 复制并粘贴整段函数
→ confirm-shell --expected-host ... --confirm
→ handoff --to agent --confirm → exec
```

`src/cli.ts` 将 19 个子命令平铺在帮助中。`exec` 已经支持自动生成 request_id，但教程仍要求用户管理编号。交还人工后，`src/session.ts` 会撤销 shell 确认，文档要求重新生成、粘贴、确认、交接。异常路径还要求区分恢复远端任务与恢复本地锁。

这些规则部分有合理的内部用途，但不应成为正常使用的前置课程。仅增加 AGENTS.md 或缩短教程，无法解决跨终端复制和多次交接的根本摩擦。

### 为什么限制落在服务器

`src/shell.bash` 是在所选目标 shell 内定义的临时函数。它解码命令，启动目标机上的 Bash 子进程，回传开始帧、结束帧和退出码。因此当前检查的是**实际执行命令的目标 shell**，通常就是堡垒机菜单后进入的服务器；升级本机 Bash 不会改变它。

这与本地 Bun、tmux、模型是否多模态无关。capture、人工终端操作本身也不要求目标 Bash >=4；该限制来自整改前的 `bash-v1` 执行配置，当前已按版本矩阵调整为 >=3.2。

临时入口还有一个用途：连接退回上一级 shell 后，随机命名、未导出的函数通常不存在，原执行载荷就不会直接作为通用脚本运行。这解释了为什么需要目标 shell 配合，不能据此证明必须使用 Bash 4。函数在当前 shell 执行的语义见 [GNU Bash 文档](https://www.gnu.org/s/bash/manual/html_node/Shell-Functions.html)。

### Bash 4 下限的实际证据

整改前发现两处硬编码拒绝（当前代码已调整，下列记录为原问题定位）：

- `src/shell.bash`：初始化要求 `BASH_VERSINFO[0] >= 4`。
- `src/protocol.ts`：握手解析拒绝 `major < 4`。

当前 helper 没有发现关联数组、mapfile 等必须依赖 Bash 4 的用法。2026-10-16 在本机 `/bin/bash` 3.2.57 上做了隔离实验：只在内存中将初始化版本判断放宽至 3，未修改仓库执行代码，也未连接远端。

| 检查 | 结果 |
|---|---|
| 原始版本判断 | 拒绝 Bash 3.2，函数未定义 |
| 放宽判断后的 hostname/user/cwd 握手 | 返回有效字段和 major=3 |
| 普通输出、stderr、退出 7 | helper 发出 BEGIN 和 END，END 携带 7 |
| 子命令 cd/export | 没有改变父 shell 的目录及变量 |
| 带末尾换行的命令载荷 | 正常执行 |
| 父 shell 开启 errexit | 返回 UNSUPPORTED_ENV |

这证明“现有 helper 必须 Bash 4”缺少依据，**不代表已经认证 Bash 3.2 完整可用**。上述实验没有覆盖真实 tmux/PTy 链路、全部崩溃恢复测试或真实堡垒机，现有解析器仍会拒绝 major=3。

## 方案比较

| 方案 | 上手复杂度 | 远端要求 | 评估 |
|---|---|---|---|
| 只改 README / AGENTS.md | 仍需多步初始化和复制 | 不变 | 只能辅助，不能作为整改主体 |
| 只将 Bash 下限改成 3.2 | 不变 | 仍绑定 Bash | 适合作为有验证的短期兼容修正 |
| 连接、交接与恢复编排 | 正常路径收敛为连接和交接 | 先保持当前执行配置 | 推荐作为本次整改主体 |
| 增加可移植 sh 协议 | 减少部分环境的兼容障碍 | 已验证的 sh 能力与少量工具 | 后续按需求独立立项，不阻塞入口简化 |
| 只有原始输入与文本快照 | 操作可简单 | 不要求特定 shell | 可作显式终端模式，无法提供可靠 completed/exit_code |
| 改用独立 SSH exec 通道 | 普通 SSH 可简化 | 取决于 SSH 服务和目标配置 | 可作未来后端，不能普遍替换交互堡垒机场景 |
| 远端安装 Agent/服务 | 可提供更强结果通道 | 安装、升级与服务权限 | 当前场景收益不足，不建议作为此次整改前提 |

OpenSSH 的 ControlMaster 复用的是同一网络连接上的多个 session，见 [ssh_config](https://man.openbsd.org/ssh_config#ControlMaster)。据此不能推断新 session 会继承另一个交互 shell 中的目录、菜单选择或嵌套 SSH 连接；切换 SSH 后端需要单独评估这些场景。

## 第一步：完成操作简化的最小闭环

### 用户只负责连接、认证和交接

计划中的主流程：

```text
用户：remote-terminal connect bastion
工具：创建专用 tmux 会话并生成 session_id，显示在本地状态栏，进入 SSH 终端
用户：完成密码/MFA/菜单，进入目标服务器普通 shell
用户对 Agent：登录好了，可以接管，用共享终端帮我检查磁盘
Agent：通过 skill 查询唯一会话的 session_id，调用 ready 完成准备与校验
Agent：开始执行已经获用户授权的任务
```

`bastion` 是用户已有 SSH 配置别名，不另建 Bridge 主机配置。`connect` 合并 start、SSH 启动和可写 attach；首期面向真实终端运行，不假装能在没有 TTY 的 Agent 工具调用中显示人工登录界面。独立二进制作为普通用户主入口，源码构建留在开发文档。

一次交接确认针对明确选定的共享会话，并表示“已经完成登录和目标选择，现在可操作空闲 shell”。不要求用户再说 hostname。用户未给出 session_id 时，Agent 只在本地查询结果唯一且已授权时自动选取；多个候选时集中确认会话，不猜最近使用。不能由 Agent 看见一个提示符就自行授权。

`ready` 的具体工作由工具承担：

1. 核对绑定、权限、未决任务和当前控制权。
2. 先保存客户端恢复信息并将已知人工客户端切为只读，再在用户明确确认的 shell 中自动发送内置临时 helper，不要求复制代码或打开第二个终端。
3. 完成能力握手，读取 hostname/user/cwd 并验证协议字节能够往返；用户显式指定预期主机时才额外匹配。
4. 一并完成 Agent 控制权交接，返回 `ready=true` 与目标信息。

正常用户不需要理解其中的初始化代次、随机函数名或状态机。现有底层命令保留为高级接口，主帮助与教程只展示 connect、status、交接和恢复入口。

**这是明确的契约变更**：旧方案要求人工粘贴；新方案允许工具在本次用户明确交接之后自动初始化。实施时必须同步修改 Solution.md、根 AGENTS.md、使用说明及相关测试。初始化过程要验证 PTY 输入限额、传输完整性及确认期间的人工输入协调，不能简单把整段函数快速模拟键入后固定 sleep。

### 四条用户路径与命令职责

以下接口已在当前源码中实现；实际安装包须通过 capabilities/help 确认，当前使用说明见 README。

| 用户意图 | 用户操作 | 工具/Agent 负责 |
|---|---|---|
| 首次使用 | 终端运行 `remote-terminal connect bastion`，完成人工登录 | 检查本地依赖、创建受管会话、显示 session_id、启动 SSH、进入可写终端；展示交接提示 |
| 交给 Agent | 单会话说“登录好了，可以接管，帮我检查磁盘”；多会话时附上 session_id | 从本地记录解析 session_id，调用 `ready --session-id SESSION_ID --confirm --json`，成功后执行已授权任务 |
| 临时自己操作 | 在聊天中说“把这个会话交回我” | 对上下文中明确的 session_id 调用 takeover；空闲时恢复原客户端输入权限，执行中先完成协作接管；不自动中断远端任务 |
| 异常后继续 | 接管并自行处理后，说“已处理完，登录和目标选择都已完成，现在可以继续” | resume 对同一 session_id 定位未决记录、登记处理、重新准备；旧命令不重发，旧 unknown 不改为成功 |

聊天里的自然语言由宿主 Agent 理解，Bridge 不引入聊天服务或模型依赖。不使用 Agent 时，可在本地通过同样的 ready/takeover/resume 入口交互完成；“不需要第二终端”的验收首先针对用户与可调用本地 CLI 的 Agent 协作场景。

### session_id 何时生成、如何提供

session_id 标识本地 Bridge 共享会话，取代正常路径中的“用户提供 hostname”来选择操作对象。它不代表远端主机身份，也不是授权凭证。

| 标识 | 生成与用途 | 用户是否需要管理 |
|---|---|---|
| session_id | 创建本地绑定时由工具生成；定位同一个共享会话 | 单会话无需复制；多会话可提供以明确选择 |
| request_id | 每条命令提交前由 Agent 或 CLI 生成；追踪结果与防止重复提交 | 无需管理，由 Agent 保留并查询 |

具体约定：

1. `connect` 创建会话并登记本地绑定时生成、持久化 session_id，在用户开始输入登录信息前展示。复用现有绑定的随机 `id` 作为公开 session_id，保持至少 128 位随机值；与 tmux 内部 `$0` 等 session ID 分开。
2. 在 Bridge 管理的本地 tmux 状态栏持续显示完整 session_id 与会话别名，窗口变化时仍可重新显示或复制。状态栏由本地固定格式渲染，不把编号写入远端命令、提示符或认证输入；不修改外部 tmux 会话的全局配置。
3. 同时展示交接提示；`list --json`、`status --json` 返回同一 session_id，方便 skill 获取。单会话正常路径无需用户复制编号；有多个会话时可复制“使用 session_id=...，我已登录，可以接管，检查磁盘”。
4. 当前绑定存续期间 session_id 不因普通人工/Agent 交接而变化；重新创建或重新绑定产生新 ID。连接变化、人工接管与准备失败仍撤销旧 shell 确认，通过内部代次管理，不能因为 session_id 未变就继续执行。
5. 新增 `--session-id` 按完整 ID 精确解析，只能选择已经登记且有权限的绑定；不存在或已失效时明确报错，不回退到别名、active pane 或最近会话。与 `--session` 同时提供时拒绝，避免不同选择器冲突。旧 `--session` 行为保留兼容。
6. hostname/user/cwd 在准备握手时自动读取，标记为 shell 自报信息供展示。没有用户预期 hostname 时不再做独立主机名匹配；不得声称 session_id 提供了同等的目标主机校验。用户仍决定自己登录到哪里，并明确交接当前会话。

本地状态栏示意，编号在真实界面使用完整值：

```text
Bridge · remote · session_id=19b0b332d87e4df4ba70a47a549c5216
登录并选好服务器后，对 Agent 说：登录好了，可以接管，用共享终端帮我检查磁盘。
```

编号从创建时就可见，但“会话已创建”不代表“已经登录”。Agent 读到编号仍需本次人工交接确认，不能在用户输入密码、操作菜单期间自动初始化或采集认证内容。

### 随项目交付 Agent skill

仓库内提供 [agent-terminal-bridge skill](../skills/agent-terminal-bridge/SKILL.md)，随软件包分发；skill 主文件及其 references 自包含，可整体复制到宿主 Agent 配置的 skills 目录。安装者启用并确认宿主发现该 skill，不能把 CLI 安装成功等同于 skill 已加载。非 skill 宿主使用 [AGENTS.md 示例](../examples/AGENTS.md) 中的等价指引入口。

skill 负责识别“共享终端”“session_id”和共享终端上下文中的“登录好了、交回我、继续”等意图，查询 CLI 能力与本地会话，选择精确 session_id，准备、执行与恢复。不会把普通的“登录好了”扩展到其他系统，也不会重新发起 SSH、自动认证或绕过宿主授权。

新接口已返回 `features.connect`、`features.session_id_selection`、`features.ready`、`features.takeover`、`features.resume` 能力字段。skill 必须先检查实际安装包的这些字段与帮助；旧包未提供时不尝试新命令。旧包仅按其契约使用已经准备好的会话，未准备时明确报告差异；不为模拟新流程自动串接旧命令或粘贴 helper。

主帮助突出 connect、status、takeover、resume；ready、exec、request 放在 Agent 集成说明，bind、send、recover-lock 等留在高级参考。旧命令继续可用，不立即删除或改变其语义。

`connect` 的明确规则：

- `connect bastion` 中 bastion 仅是 SSH 配置别名，不是最终服务器 hostname。首个受管会话仍可用 remote，同时提供独立的 session_id。
- 带目标表示创建该连接；若目标会话名已占用，展示冲突并让用户选择已有会话或新名称，不能把另一个目标的旧会话直接返回。现有 start 的复用行为不能原样套入新入口。
- 不带目标时只选择已登记会话：一个明确候选可进入，多个候选展示列表；非交互调用返回选择要求，不猜“最近使用”。Agent 一旦取得明确 session_id，后续始终传入该 ID。现有命令的默认会话解析保持兼容。
- 进入已有 Agent 会话默认只读；需要写入时走 takeover。断开观察客户端不等于关闭 SSH，关闭会话仍是独立的显式操作。
- 无真实 TTY 时，在创建 SSH 连接前拒绝交互 connect，给出可复制到本地终端的连接命令。不得创建一个用户看不见的登录界面后宣称连接成功。
- connect 成功仅代表本地交互入口已打开，不能报告“远端已就绪”。首次缺少依赖给出本平台安装指引，不自动修改系统或 SSH 配置。

### ready 必须是事务，不能串接三个 CLI

现有 initialize、confirmShell、handoff 分别获取和释放资源锁。直接按顺序调用这三个 CLI 会留下插入人工输入或其他写入的窗口。应在会话编排层建立一次有界的准备事务，复用其内部能力而非递归加锁：

1. 按 session_id 解析唯一绑定并取得资源锁，验证同一绑定代次、有效 exec 权限、无未决任务，以及本次会话与空闲 shell 交接确认。
2. 持久化“准备中”及客户端恢复信息，阻止其他写入，再冻结已知人工客户端；未完成冻结不得发送 helper。短期元数据锁不跨终端等待持有。
3. 订阅输出后传输内置 helper，采用经真实 PTY 验证的有界传输方式；现有测试通过本地文件 source helper，不能代替自动传输验收。
4. 验证新鲜握手、同一会话代次和能力，保存 shell 自报的 hostname/user/cwd，原子提交确认与 Agent 控制权，再返回 ready。hostname 默认用于展示，不强制要求用户提供预期值；显式启用高级主机检查但不匹配时不得执行用户命令。
5. 已开始传输后失败、超时或崩溃，保留准备失败/需人工处理状态，不自动重新发送或恢复可写；明确接管后才允许人工处理残留输入。发送前确定未产生影响的失败可恢复原客户端标志。

重复 ready 不能无条件重装 helper；已准备会话在同一绑定、代次与控制权有效时可返回现状，但不把历史握手当成远端持续在线的证据。人工接管后重新 ready 必须基于新交接确认。准备记录需要 session_id、绑定代次与操作标识，崩溃后状态查询能解释停在哪一步。

### 状态和恢复应直接告诉用户下一步

普通输出只展示会话、目标证据、状态和下一步，例如：

```text
会话 remote · session_id=19b0b332d87e4df4ba70a47a549c5216
上次 shell 自报目标：web-01
状态：结果未确认，远端任务可能仍在运行
下一步：请接管终端，检查并处理当前任务。
```

| 面向用户的状态 | 依据与下一步 |
|---|---|
| 等待人工准备 | 绑定有效但未确认 shell；完成登录和目标选择后交接，不能声称已识别登录界面 |
| 正在准备 | 准备事务存在；等待其有界结果，禁止并发写入 |
| 可执行 | 绑定、权限、确认、控制权和未决记录满足条件；每次 exec 仍重新校验 |
| 执行中 | 当前请求存在；等待、查询，或显式接管 |
| 需要人工处理 | unknown、初始化传输不明、损坏状态或遗留锁；给出与原因对应的下一步 |
| 连接已结束/绑定失效 | 由本地对象事实判定；有未决请求先处理记录，再显式重建连接 |

JSON 保留现有状态维度、退出码和错误语义，拟新增可选的展示状态与结构化下一步（动作、所需参数、是否需人工确认）。下一步由受信任的本地状态和错误码生成，不把远端输出转换为可执行建议。status 继续只读，不因“智能诊断”发送探测或执行恢复。

takeover 与 resume 的职责必须分开：takeover 让人能够检查；resume 在用户确认处理完成后恢复自动执行资格。resume 不意味着“重试上一条命令”，也不意味着“重新登录”。本地死锁检查可以由工具定位具体锁并在明确恢复操作中处理；活锁、身份不明或不完整 owner 记录仍停止并提示维护。运行中的接管必须等待执行协调者确认，不能把“已请求”展示为“已接管”。

session_id 与命令 request_id 分开：后者只用于追踪单条命令。自动 request_id 是人类用户的便利，不应削弱 Agent 的故障定位：可重试调用链中的 Agent 应在提交前生成并保留稳定 ID；使用 CLI 自动编号且响应丢失时，先查该 session_id 的活动请求与有界的最近请求元数据。若不能唯一定位，停止并请求核对，不能新建编号补发。历史查询只保存必要元数据，不为简化恢复而持久化命令正文或输出。

### Agent 不再现场教用户协议

Agent 的常规路径只需会话查询、ready、exec 和请求查询。配套 skill 提供通用指引，明确哪些操作可由工具完成，哪些情况必须交回用户；capabilities 和 status 返回可执行的下一步。

- 请求编号默认自动生成并返回，仍允许调用方提供固定编号，保留去重语义。Agent 保存编号，不能用新编号重试未知结果；丢失响应后先通过状态和历史定位请求。
- 用户提供的 session_id 精确选择；未提供时只有唯一且已授权的候选才自动选择。存在多个候选时要求选择，不能猜最新会话，不要求用户用 hostname 代替会话选择。
- `status` 显示用户能理解的状态，例如“等待人工登录”“可执行”“需要人工处理”，详细绑定与协议数据继续放在 JSON 内。
- 空闲交接自动完成必要的内部状态变更；下一次 ready 可在明确交接后验证已有入口，必要时重新准备，避免让用户重复粘贴。
- 计划中的 `takeover`、`resume` 封装现有接管、核对未决请求、恢复和重新准备步骤。恢复向导只汇总必要问题，不让用户选择 execution/metadata/audit 锁范围。无法证明本地持锁者已死亡时仍拒绝清理。
- 错误给出位置、原因和一个建议动作。doctor 分开报告本地运行环境与目标执行能力；未准备目标时写“尚未检测”，不能把本机 Bash 版本当作远端结论。

## 独立兼容工作：Bash 下限通过验证修正

先将 Bash 3.2 纳入完整协议和集成测试，验证通过后同步放宽 helper 与解析器的版本门槛。不能只改 README，也不能仅删一个判断便宣称支持。

这一步直接缓解旧 Bash 环境，工作量小于重写协议；但仍是 Bash 配置，不解决服务器使用 dash/ash 的问题，也不作为服务器升级要求的长期替代。

## 后续可选工作：可移植 shell 执行协议

这一项改变命令解释语义和兼容矩阵，代价高于入口封装。本轮不把它列为操作简化的必交付项；先收集实际用户被 Bash 限制阻塞的环境，再决定是否立项。即使新增 sh-v1，也先显式选择 profile，不在本次整改中直接替换 bash-v1 默认值。

增加小型、内置的 `sh-v1`，以经过验证的 POSIX shell 语法实现临时入口。使用函数、case、printf、子进程与退出状态，替换 `[[ ]]`、BASH_VERSINFO、`$BASH` 和 Bash 专属启动选项。标准函数与退出状态语义见 [POSIX Shell Command Language](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)。

采用以下边界：

- 面向已验证的 Bourne 兼容 shell，首先验证 Bash 3.2/4/5、dash、BusyBox ash。fish/csh、受限 shell 不因服务器存在 `/bin/sh` 就自动算作兼容。
- helper 负责协议，用户命令在独立 `sh` 子进程中执行，继承目录与导出环境，stdin 仍为 `/dev/null`。清理隐式启动环境并验证不同 shell 的选项、trap 行为。
- 保留当前 Base64 传输时，实际检测编码/解码往返和所用工具；`sh-v1` 不等于“服务器零依赖”。缺少能力时报告具体缺项，不要求用户笼统升级 Bash。
- Agent 必须获知实际 profile 与命令语义。Bash 数组等脚本通过显式 Bash 配置执行，不能悄悄按 sh 解释。旧 bash-v1 会话保持原语义；若未来改变新会话默认值，单独评审迁移，并显式重新准备。
- 保留随机、会话内且不导出的入口。入口失效时停止执行，不回退成任意 `sh -c 用户命令` 输入，不根据终端文字猜测命令成功。
- 不写 shell 启动文件、不部署远端包、不增加常驻服务。初始化仅在明确交接后进行。

POSIX 是降低依赖的设计依据，兼容性仍须用实际 shell 与完整终端链路证明。此阶段不阻塞第一步的入口简化。

## 必须保留的行为

用户界面简化后，绑定身份校验、互斥、发送前持久化和 unknown 语义仍在内部保留。超时和断线时不能自动重试、重连或发送 Ctrl+C；进入菜单、密码输入、编辑器等状态时不能自动初始化。

接管/恢复可以合并成一次向导，但“远端任务已处理”的决定仍需用户作出。已发生的未知结果不改写为成功，也不能为方便继续执行而直接清除活动任务或删除未知归属的锁。

不支持执行协议的目标可以保留文本查看和明确授权的终端操作；能力返回 exec=false，不把 send+capture 包装成有退出码保证的 exec。

## 实施范围与验收

| 顺序 | 主要修改 | 完成门槛 |
|---|---|---|
| P0-A：入口与展示 | CLI 的 connect、session_id 精确选择与状态栏展示、短帮助、可读状态；独立二进制用户入口 | 零配置创建与进入会话；登录前显示编号；无 TTY、已有会话、目标冲突、多会话选择行为明确 |
| P0-B：正常交接 | 会话编排层的 ready 事务、准备记录、自动传输；配套 skill 与安装指引 | 无需提供 hostname、复制 helper 或第二终端；skill 能正确选择会话与识别旧版；真实 PTY 传输、并发与崩溃测试通过 |
| P0-C：异常闭环 | takeover/resume、状态定位请求和本地锁诊断 | 超时、断线、CLI 崩溃后可清楚恢复；未知任务不会重发，活锁不会被抢占 |
| P1：实际兼容（独立交付） | shell 模板、握手校验、测试 fixture、兼容文档 | Bash 3.2/4/5 的真实 tmux 执行与异常测试通过，再发布支持声明 |
| P2：可移植执行（需求确认后） | sh-v1 模板与 profile 字段、启动环境、协议及适配测试 | dash、BusyBox ash 与 Bash 作为 sh 的矩阵通过；旧配置语义不变 |

P0-A/B/C 构成一次完整的可用性整改；可以分批实现，但只完成入口包装不算完成验收。CLI 保持参数和输出职责，会话编排负责组合事务，tmux 后端负责客户端和输入，executor/state 负责准备与执行记录；不为此增加守护进程或新运行时依赖。

新增验证至少包括：重复 connect 不串目标、无 TTY 不残留新连接、多会话不误选、session_id 与别名冲突/失效/重建、状态栏编号与 JSON 一致、两次 ready 竞争、冻结客户端失败、传输中断、握手后提交前崩溃、初始化期间新增可写客户端、未提供 hostname 的正常交接、高级主机检查不匹配、接管协调超时、自动命令编号响应丢失，以及旧 CLI/JSON 契约回归。构建涉及的内置 helper 必须覆盖源码、bundle 和独立二进制三种形态。

用户验收标准：

1. 安装完成后，首次使用者只读一屏说明即可连接；扣除认证和菜单耗时，目标在两分钟内完成首次授权执行。
2. 用户正常路径只运行一个连接命令，并作一次当前共享会话的交接确认；单会话无需复制 session_id，多会话可用编号明确选择。不提供 hostname，不接触 shell-init、confirm-shell、handoff、命令 request_id 或锁范围。
3. 同一终端可见人工登录过程和后续 Agent 命令输出，交回人工时无需重新建立 SSH。
4. 本地依赖与远端能力的诊断明确分栏，测试中刻意使用不同的本机/目标 Bash 版本，避免混淆。
5. 初始化中断、无效 session_id、高级主机检查不匹配、SSH 退出回菜单/上一级 shell、协议字节过滤、命令超时及执行期间接管都能停止写入并给出明确下一步。
6. 自动测试外，至少让两名未参与开发的使用者完成冷启动验收，并在获授权的真实堡垒机上验证一次。未完成前不宣称流程或兼容性整改已验收。

运行时已实现上述 P0/P1 入口、准备事务、状态与恢复编排，文档与 skill 同步更新。旧 confirm-shell 继续保留 expected-host 契约。真实远端和首次使用者验收未被自动化测试替代；全量检查、构建与外部验收状态统一记录在整改验证文档，尚未取得证据的门槛不标为完成。
